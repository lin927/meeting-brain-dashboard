# 知识库分类与元数据

本文记录公司 RAGFlow 知识库的分类树和元数据约定。会议助手按此上传会议；需求、设计等其它资料由对应系统写入**同一套字段**，不另起一套。

现状：四个知识库仍按会议种类分库。会议上传已写 `category` / `category_label`、`doc_kind=meeting`，并过渡期双写 `meeting_type`。需求、设计等其它资料由对应系统按同一套字段写入，不走会议助手。

---

## 1. 原则

1. **分类树 ≠ 知识库。** `category` / `doc_kind` 是检索标签；四个 RAGFlow 库是权限和隔离。类别变多时先加元数据，不先拆库。
2. **两级必写，第三级选写。** 一级是业务域，二级是资料形态。不要把「需求文档」做成一级类别。
3. **会议只是一种资料。** 项目库可以混放会议、需求、设计等；公司管理 / 公司运营的会议元数据不被项目资料冲掉。
4. **有关才写。** 空值不写入 RAGFlow。项目字段只出现在项目相关文档；`meeting_id` 只出现在会议。
5. **覆盖主键按形态分开。** 会议用 `meeting_id`（钉钉听记 id）；其它资料用 `doc_id`。二者不要混用。
6. **代码用英文，展示用中文。** `category`、`doc_kind` 存稳定英文代码，另写 `*_label` 给人看、给过滤提示用。
7. **元数据只放能过滤、能列表预览的短信息。** 全文总结、需求正文、设计说明放文档里供切块检索。短摘要、自由标签可以进元数据；不要用标签冒充分类树。

本机会议助手的界面仍叫「类型」，SQLite 仍用 `scope`。那些是本机分类用语，只在**上传时**映射成知识库字段。

---

## 2. 分层

| 层 | 字段 | 作用 | 约定 |
|---|---|---|---|
| 0 知识库 | RAGFlow dataset | 权限、切块、隔离 | 先保持四个库；新类别先挂到现有库 |
| 1 类别 | `category` / `category_label` | 这篇属于哪块业务 | 每篇必写 |
| 2 资料类型 | `doc_kind` / `doc_kind_label` | 这篇是什么形态 | 每篇必写 |
| 3 细分 | `doc_subtype` | 周例会 / 立项会 / PRD 等 | 暂不写，有明确检索需求再加 |
| 4 身份与上下文 | 见第 5 节 | 覆盖、关联、过滤 | 按类别和资料类型条件写入 |

个人会议不上传，不进入任何知识库类别。

---

## 3. 一级类别 `category`

| 代码 | 中文 | 放什么 | 先进行哪个库 | 附加字段 |
|---|---|---|---|---|
| `project` | 项目 | 某个具体项目的全过程资料 | 项目知识库 | 必有 `project_code`（有正式名则写 `project_name`） |
| `company_mgmt` | 公司管理 | 治理、管理例会、管理层决策 | 公司管理知识库 | — |
| `company_ops` | 公司运营 | 公司级运营例会与运营资料 | 公司运营知识库 | — |
| `dept_mgmt` | 部门管理 | 部门例会、部门规范 | 部门知识库 | 必有 `dept` |
| `marketing` | 市场营销 | 市场活动、方案、客户交流 | 先放公司运营库 | 先靠元数据区分，量上来或权限要分开再拆库 |
| `research` | 技术研究 | 预研、论文、技术分享 | 先放公司运营库 | 同上 |
| `policy` | 公司制度 | 制度正文、解读、宣贯会 | 先放公司管理库 | 制度正文用 `doc_kind=policy` |
| `project_case` | 项目案例 | 跨项目复盘、样板工程 | 先放项目知识库 | 可关联 `project_code`，检索按案例横查 |

### 命名约定

- **用「公司运营」，不用「项目运营」。** 现有运营例会已在公司运营库。某个项目怎么推进，归 `project`；公司级 PMO / 运营机制，并进 `company_ops`。
- **公司制度、项目案例是一级类别**（要按「所有制度」「类似案例」横着搜）。制度正文、案例文章本身仍是 `doc_kind`。
- 扩类别：只增加本表的一行代码和中文，不改字段名。

---

## 4. 二级资料类型 `doc_kind`

各类别共用同一套代码。不是每个类别都要出现全部类型；没有的就不写那种文档。

| 代码 | 中文 | 常见类别 | 身份字段 |
|---|---|---|---|
| `meeting` | 会议 | 所有类别 | `meeting_id`、`start_time`、`attendees` |
| `requirement` | 需求文档 | 项目为主 | `doc_id`，建议有版本 |
| `design` | 设计文档 | 项目、技术研究 | `doc_id`，建议有版本 |
| `review` | 评审文档 | 项目、技术研究 | `doc_id`，可加结论 |
| `change` | 变更文档 | 项目 | `doc_id`，可加变更单号 |
| `communication` | 沟通记录 | 项目、市场 | `doc_id`；不要写 `meeting_id` |
| `policy` | 制度 | 公司制度、公司管理 | `doc_id` 或制度编号 |
| `case` | 案例 | 项目案例 | `doc_id`；可关联原项目 |

项目类别下当前就要能用的组合：`meeting`、`requirement`、`design`、`review`、`change`、`communication`。

扩资料类型：只增加本表的一行，不改字段名。

---

## 5. 字段一览

空值、空字符串不写。数组（如标签、别名）写成顿号拼接的字符串。

### 5.1 每篇都写

| 字段 | 含义 | 取值 |
|---|---|---|
| `category` | 一级类别代码 | 见第 3 节 |
| `category_label` | 一级类别中文 | 与代码对应 |
| `doc_kind` | 资料类型代码 | 见第 4 节 |
| `doc_kind_label` | 资料类型中文 | 与代码对应 |
| `title` | 标题 | 原文 |
| `abstract` | 短摘要 | 一两句话，不超过 300 字。有则写，没有不写。不是全文总结 |
| `tags` | 自由标签 | 顿号拼接。模块、主题、客户等关键词；有则写 |
| `source` | 来源 | 会议常见 `dingtalk` / `import`；其它系统自定（如 `drive`、`wiki`） |
| `uploaded_by` | 上传人 | 操作者姓名 |
| `uploaded_at` | 上传时间 | ISO 8601 |

`category` / `doc_kind` / `project_code` / `dept` 是结构化分类，**不要再重复写进 `tags` 来冒充。** `tags` 只放这些字段表达不了的主题词（如「爆破级配」「巡检」「周例会」）。没有标签就省略该字段。

`abstract` 给列表和过滤用：需求可写一句话目标，设计可写方案要点，会议写总结首段。超过 300 字截断。没有短摘要就省略，不要用全文或逐字稿填。

### 5.2 仅会议 `doc_kind=meeting`

| 字段 | 含义 | 说明 |
|---|---|---|
| `meeting_id` | 听记 ID | 钉钉 `task_uuid`。四个库都靠它认同一场会，覆盖/撤回的主键 |
| `start_time` | 开始时间 | ISO 8601 |
| `attendees` | 参会人 | 姓名串 |

会议的 `tags`、`abstract` 走第 5.1 节（每篇通用），不单列为会议字段。部门会过渡期标签里可能仍有部门名；结构化筛选用 `dept`。

会议 `abstract`：取本机「总结」的首段，截到 300 字；没有总结则不写，不要用逐字稿或整篇记录冒充摘要。

过渡期会议可**双写** `meeting_type`（中文：公司管理 / 公司运营 / 项目 / 部门），方便旧过滤。新检索应改用 `category`。稳定后停写 `meeting_type`。

### 5.3 仅非会议

| 字段 | 含义 | 说明 |
|---|---|---|
| `doc_id` | 资料稳定 ID | 钉盘 fileId、知识库节点、变更单号等。覆盖靠它 |

不要写 `meeting_id`（也不要写成空字符串）。可选：`version`、`status`、评审结论、变更单号等，按资料类型需要再加，不作为分类树。

### 5.4 仅项目相关（`category` 为 `project` 或 `project_case`）

| 字段 | 含义 | 说明 |
|---|---|---|
| `project_code` | 项目编号 | 与数智系统对齐；`project` 必填 |
| `project_name` | 项目正式名 | 有则写 |
| `project_aliases` | 项目别名 | 称呼表里的别名，有则写，顿号拼接 |

### 5.5 仅部门管理

| 字段 | 含义 | 说明 |
|---|---|---|
| `dept` | 部门名 | 结构化筛选；不要只靠 `tags` |

### 5.6 不写入 RAGFlow 元数据

本机组装但排除：听记链接 `url`、目标库 id、`visibility`、上传时间的本地可读文案。逐字稿默认不上知识库。

**全文总结、记录、待办、需求/设计正文**写在文档里供切块，不算 meta。只有截过的短摘要进 `abstract`。

---

## 6. 四个知识库怎么挂

| 知识库 | 先收哪些 `category` | 说明 |
|---|---|---|
| 公司管理 | `company_mgmt`，以及暂挂的 `policy` | 今天主要是管理会 |
| 公司运营 | `company_ops`，以及暂挂的 `marketing`、`research` | 今天主要是运营会 |
| 项目 | `project`，以及暂挂的 `project_case` | **混合资料库**：会议 + 需求/设计/评审/变更/沟通等 |
| 部门 | `dept_mgmt` | 今天主要是部门会 |

会议助手仍然只上传会议，按本机「类型」选库（与现在相同）。需求、设计等由其它系统写入对应库，带上同一套 `category` / `doc_kind`。

---

## 7. 从现有会议怎么映射

本机「类型」→ 上传元数据：

| 本机类型 / 现 `meeting_type` | `category` | `category_label` | `doc_kind` | 知识库 |
|---|---|---|---|---|
| 公司管理 | `company_mgmt` | 公司管理 | `meeting` | 公司管理 |
| 公司运营 | `company_ops` | 公司运营 | `meeting` | 公司运营 |
| 项目 | `project` | 项目 | `meeting` | 项目 |
| 部门 | `dept_mgmt` | 部门管理 | `meeting` | 部门 |
| 个人 | （不上传） | — | — | — |

其它系统写入需求文档示例：`category=project`，`doc_kind=requirement`，`project_code=…`，`doc_id=…`，不写 `meeting_id`。

历史上传若只有 `meeting_type`、没有 `category`：检索时可把 `meeting_type` 映射为上表；没有 `doc_kind` 的旧会议篇先当作 `meeting`。补写任务应同时写上 `category` / `doc_kind`，并删除更早的 `type` / `type_label`。

---

## 8. 检索怎么切

先选知识库（缩小范围），再用元数据过滤。

| 问题 | 库 | 过滤 |
|---|---|---|
| 这个项目会上定了什么 | 项目 | `category=project` + `project_code` + `doc_kind=meeting` |
| 这个项目的需求 | 项目 | `category=project` + `project_code` + `doc_kind=requirement` |
| 这个项目的设计 | 项目 | `category=project` + `project_code` + `doc_kind=design` |
| 运营例会里怎么说的 | 公司运营 | `category=company_ops` + `doc_kind=meeting` |
| 某部门周会 | 部门 | `category=dept_mgmt` + `dept` + `doc_kind=meeting` |
| 公司制度怎么规定的 | 公司管理（先） | `category=policy` 或 `doc_kind=policy` |
| 有没有类似项目案例 | 项目（先） | `category=project_case` |

同一场听记覆盖、撤回：按 `meeting_id` 在四个库里查，不靠文件名。

---

## 9. 谁写哪些文档

| 资料 | 谁写入 | 说明 |
|---|---|---|
| 会议 | 会议助手 | 只上传会议；本机选类型后映射 `category` + `doc_kind=meeting` |
| 需求 / 设计 / 评审 / 变更 / 沟通 | 钉盘、知识库或其它业务系统 | 写入项目库（或将来对应库），遵守本文字段 |
| 制度、案例、市场、预研 | 对应业务系统 | 先挂在第 6 节的现有库，带正确 `category` |

会议助手不负责把需求文档传进知识库。

---

## 10. 先不要做的

- 不要把需求、设计提升成一级 `category`。
- 不要为每个类别立刻新建 RAGFlow 库。
- 不要用 `tags` 冒充分类树（类别、资料类型、项目编号、部门名都有正式字段）。
- 不要把整篇总结、记录或逐字稿写入 `abstract`。
- 不要在需求/设计上写 `meeting_id`。
- 不要把「项目运营」做成与「公司运营」「项目」并列的含混类别。
- 第三级 `doc_subtype` 等有「周例会 vs 立项会」这类稳定检索需求再加。

---

## 11. 落地顺序（会议助手）

1. **已完成：** RAGFlow 会议元数据用 `meeting_type`（中文四类），不再写 `type` / `type_label`；会议篇写 `doc_kind=meeting`。启动时补写已上传会议，并清掉旧 `type`。
2. **已完成：** 上传时写 `category` / `category_label`，由本机类型按第 7 节映射；会议继续双写 `meeting_type`。部门会有标签时写 `dept`。启动补写会给已上传会议补上这些字段。会议本机标签已写入 `tags`。
3. **已完成：** 会议上传写短摘要 `abstract`（本机总结里的「一句话结论」或首段，≤300 字；没有总结则不写）。标签仍写 `tags`，且不再把类别/项目名/部门名重复塞进标签。
4. **随后：** 检索以 `category` 为准；部门会在界面上结构化选部门（现在仍从标签取 `dept`）。
5. **稳定后：** 停写 `meeting_type`。其它系统按本文接入项目库中的非会议资料，同样带 `abstract` / `tags`（有则写）。
